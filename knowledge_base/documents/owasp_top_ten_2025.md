# OWASP Top 10 - 2025 The Ten Most Critical Web Application Security Risks

Source: https://top10.owasp.org/2025/
Retrieved: 2026-10-14
Author: OWASP Foundation

## A01:2025 - Broken Access Control
Access control enforces policy such that users cannot act outside of their intended permissions. Retains the #1 position in the 2025 rankings. Access control failures typically lead to unauthorized information disclosure, modification, or destruction of data, or performing a business function outside the user's limits. In the 2025 edition, Server-Side Request Forgery (SSRF) and Open Redirects have been officially incorporated into Broken Access Control, recognizing that forcing an application server to act as an unauthorized proxy or redirect to untrusted destinations represents an access control boundary violation. Common access control vulnerabilities include bypassing access control checks by modifying URLs, internal application state, or HTML forms; using custom API attack tools; permitting viewing or editing someone else's account by providing its unique identifier (Insecure Direct Object References - IDOR); missing access controls on sensitive HTTP methods (POST, PUT, DELETE); elevation of privilege (acting as an administrator without logging in); metadata manipulation (replaying or tampering with JWT tokens or cookie permissions); CORS misconfiguration permitting unauthorized API access; and SSRF attacks where attackers coerce server requests to internal backends, loopback interfaces, or cloud metadata endpoints. Prevention requires enforcing least privilege by default, denying access unless explicitly granted, centralizing authorization checks in controllers or gateway filters, disabling directory browsing, recording access control failures, and validating destination IP addresses/hostnames with strict allowlists for outbound requests.

## A02:2025 - Security Misconfiguration
Security Misconfiguration climbed significantly to #2 in the 2025 edition, reflecting the widespread complexity of multi-cloud architectures, container orchestration, microservices, and modern CI/CD pipelines. Security misconfiguration happens when security controls are inaccurately defined, implemented, or maintained, or left at default settings. Common vulnerabilities include unhardened default configurations, enabled default accounts and passwords, unnecessary enabled ports, features, components, services, or sample pages, missing or misconfigured HTTP security headers (such as Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options), overly permissive Cross-Origin Resource Sharing (CORS) configurations, verbose error messages displaying detailed stack traces or internal database error codes, misconfigured cloud storage permissions (e.g., publicly readable AWS S3 buckets, exposed Azure blobs), unpatched software or outdated container base images, and insecure configuration files with debug modes left active in production. Prevention requires automated, repeatable hardening processes, deploying environments via Infrastructure as Code (IaC) with immutable configurations, removing unused features and frameworks, disallowing default credentials, reviewing cloud permissions continuously, sending security headers, and sanitizing error responses for external clients.

## A03:2025 - Software Supply Chain Failures
A major new category for the 2025 edition, expanding and superseding the previous "Vulnerable and Outdated Components" category. Modern applications are heavily assembled from thousands of third-party open-source libraries, container registries, build plugins, and automated CI/CD distribution pipelines. Software Supply Chain Failures encompass risks introduced across the entire software development, delivery, and deployment lifecycle. Attack vectors include malicious or hijacked open-source packages in public repositories (such as npm, PyPI, Maven Central, or Docker Hub), typosquatting, dependency confusion where attackers publish malicious public packages with internal namespace names, compromised developer or maintainer accounts, malicious build-time script execution during package installation (e.g. postinstall hooks), compromised CI/CD pipelines injecting unauthorized code into release binaries, lack of cryptographic package verification, and unpatched CVEs in nested transitive dependencies. Prevention requires generating and maintaining an active Software Bill of Materials (SBOM), conducting automated Software Composition Analysis (SCA) in CI/CD pipelines, pinning exact package versions with cryptographic hash verification (lockfiles), using private artifact repositories with scoped namespaces to prevent dependency confusion, enforcing multi-factor authentication (MFA) and least privilege for CI/CD runners and package registries, signing build artifacts with digital signatures (Sigstore, Cosign), and continuously inventorying and patching dependencies.

## A04:2025 - Cryptographic Failures
Cryptographic Failures (ranked #4 in 2025, previously known as Sensitive Data Exposure) focuses on flaws related to cryptography that expose sensitive data in transit, at rest, or during processing. Sensitive data includes passwords, credit card numbers, health records, personal identifiable information (PII), secret keys, and business secrets requiring enhanced protection under regulations like GDPR and PCI-DSS. Failures occur when sensitive data is transmitted in clear text protocols (such as unencrypted HTTP, SMTP, or FTP), when broken or deprecated cryptographic algorithms are utilized (e.g., MD5, SHA-1, DES, 3DES, RC4), when default or hardcoded cryptographic keys are used, when weak random number generators (e.g., standard pseudo-random generators instead of CSPRNG) are used for key or token generation, when initialization vectors (IVs) are reused in cipher modes like CBC or GCM, and when passwords are stored using weak hashes without salt and memory-hard work factors. Prevention requires classifying all data processed, stored, or transmitted, encrypting all data in transit with modern TLS (TLS 1.3), disabling legacy cryptographic suites, encrypting sensitive data at rest using authenticated encryption (AES-256-GCM), managing keys through dedicated Hardware Security Modules (HSM) or secrets managers, and hashing passwords exclusively with adaptive, salted algorithms such as Argon2id, bcrypt, or PBKDF2.

## A05:2025 - Injection
Injection flaws (ranked #5 in 2025) occur when untrusted data is sent to an interpreter as part of a command or query. The attacker's hostile payload tricks the interpreter into executing unintended commands, evaluating code, or accessing and modifying database records without authorization. Injection encompasses SQL Injection, NoSQL Injection, OS Command Injection, Object-Relational Mapping (ORM) injection, Cross-Site Scripting (XSS), Server-Side Template Injection (SSTI), and Expression Language (EL) injection. Primary vectors include concatenating user input directly into SQL statements (`SELECT * FROM users WHERE name = ' + user`), passing unsanitized parameters into system shells (`subprocess.Popen(cmd, shell=True)`, `Runtime.getRuntime().exec()`), evaluating untrusted strings as code (`eval()`, `exec()`), and rendering user inputs directly in web templates without contextual output encoding. Prevention requires keeping untrusted data strictly separate from commands and queries: utilizing parameterized queries and prepared statements for all database operations, avoiding system shells and using argument arrays (`shell=False`), implementing strict allowlist input validation, using modern web frameworks with automatic contextual output encoding, and implementing Content Security Policy (CSP).

## A06:2025 - Insecure Design
Insecure Design (ranked #6 in 2025) focuses on risks related to design and architectural flaws. Unlike implementation bugs, an insecure design cannot be fixed by a perfect implementation because the necessary security controls were never designed into the system. Insecure design encompasses missing or flawed business logic controls, lack of threat modeling, failure to isolate tenant boundaries in multi-tenant SaaS architectures, insecure state machines allowing steps in a checkout or approval workflow to be bypassed, credential recovery flows based on weak security questions, and lack of defense-in-depth architecture. Prevention requires adopting a Secure Development Lifecycle (SDL) with application security reviews, conducting threat modeling during the architecture phase (identifying STRIDE threats and abuse cases), establishing secure design patterns and reference architectures, segregating networks and services by trust boundaries, limiting resource consumption per tenant to prevent DoS, and integrating security user stories and acceptance criteria directly into project management.

## A07:2025 - Authentication Failures
Authentication Failures (formerly Identification and Authentication Failures, ranked #7 in 2025) occur when mechanisms verifying user identity, managing sessions, or protecting credentials fail, permitting attackers to impersonate legitimate users or compromise accounts. Common vulnerabilities include allowing automated credential stuffing and brute force attacks without rate limiting or CAPTCHA, permitting weak or well-known passwords without complexity and breach checking, storing passwords in plain text or using reversible encryption, weak or insecure password recovery mechanisms, exposing session tokens in URLs, failing to invalidate session IDs during logout or password changes, missing multi-factor authentication (MFA) on sensitive accounts, hardcoding credentials, tokens, or API keys directly in source code or repositories, and predictable session token generation. Prevention requires enforcing Multi-Factor Authentication (MFA), enforcing password strength and checking against known breach databases (e.g., Have I Been Pwned), implementing robust login rate limiting and IP throttling, using cryptographically secure session identifiers stored with HttpOnly, Secure, and SameSite cookie flags, invalidating sessions on logout and idle timeouts, and keeping credentials out of source code by utilizing secrets management solutions.

## A08:2025 - Software or Data Integrity Failures
Software or Data Integrity Failures (ranked #8 in 2025) focuses on code and infrastructure that treats unverified or untrusted code or serialized objects as valid. A critical subset of this category is Insecure Deserialization (CWE-502). Applications often serialize complex objects into binary or text formats (such as Java native serialization or Python's pickle) and transmit or store them. When an application deserializes untrusted input without validation, an attacker can manipulate object structures to invoke arbitrary method chains (gadget chains), leading to Remote Code Execution (RCE), arbitrary file writes, or privilege escalation. Other vulnerabilities include unverified auto-update mechanisms downloading executable files without digital signature checks, trusting dynamic plugins or scripts loaded from unverified CDNs, and mass assignment or prototype pollution vulnerabilities where untrusted inputs modify internal object properties. Prevention requires never accepting serialized objects from untrusted sources, preferring standard, safe data interchange formats like JSON or Protocol Buffers, implementing strict object filtering (e.g., Java ObjectInputFilter), signing and verifying digital signatures on all updates and binaries, and restricting object attribute assignment to explicit allowlists.

## A09:2025 - Security Logging and Alerting Failures
Security Logging and Alerting Failures (ranked #9 in 2025, updated to place explicit emphasis on real-time alerting) addresses deficiencies in recording security events and detecting active intrusions. Without adequate logging and alerting, attacks cannot be detected, investigated, or contained, allowing attackers to maintain persistence, pivot laterally, and exfiltrate data undetected for months. Failures occur when auditable security events (such as failed logins, access control denials, server-side validation errors, exception states, privilege escalations, and sensitive data exports) are not logged, when log entries omit crucial context (timestamps, user IDs, IP addresses), when logs are stored insecurely where attackers can tamper with or delete them, when log injection occurs due to unescaped user input in log messages, and when alerts are missing or thresholds are set so high that real attacks fail to trigger incident response. Prevention requires logging all authentication, authorization, and input validation failures with sufficient context, formatting logs consistently (e.g. JSON), preventing log injection via character sanitization, transmitting logs in real-time to centralized, tamper-resistant SIEM solutions, establishing real-time alerting rules for abnormal activity, and maintaining a tested incident response and disaster recovery plan.

## A10:2025 - Mishandling of Exceptional Conditions
Mishandling of Exceptional Conditions is a brand-new category in the 2025 edition (ranked #10), consolidating weaknesses related to improper exception handling, unhandled error states, and insecure logic branching. When an application encounters unexpected inputs, network timeouts, resource exhaustion, or runtime errors, failing to handle these conditions securely can cause the application to crash, leak sensitive internals, or "fail open" — inadvertently bypassing security checks. Common vulnerabilities include "failing open" (CWE-636) where an exception during authentication or permission checking defaults to granting access instead of denying, verbose error messages (CWE-209) exposing stack traces, internal software versions, database structures, or physical file paths to attackers, unhandled NULL pointer dereferences (CWE-476) or uncaught exceptions leading to denial of service, improper handling of missing parameters (CWE-234), and generic catch-all blocks (`catch (Exception e) {}` or `except: pass`) that swallow critical errors and leave systems in inconsistent or vulnerable states. Prevention requires designing systems to always "fail secure" (defaulting to denial of access and safe aborts when errors occur), validating all inputs to prevent unexpected runtime states, implementing localized, specific exception handling rather than silent error suppression, sanitizing error responses to return generic error codes to external clients while logging detailed diagnostics internally, and rigorous unit and fuzz testing of edge cases and exceptional condition paths.
